## CATEGORY: VISUAL PROMPTS

- **RULE:** Every single visual prompt must end with the mandatory suffix. No exceptions, no shortcuts.
- **RULE:** Suffix is: `hyper-realistic, 70s progressive rock album art style, Frank Frazetta meets Syd Mead, Kodachrome film stock, heavy film grain, cinematic lighting, volumetric fog, 8k resolution, masterpiece.`
- **RULE:** Never use clean, sterile, or smooth aesthetics. Analog decay is non-negotiable.
- **RULE:** No drama references in music descriptions. Anatolian Prog Rock only.
- **RULE:** Always specify `16:9 widescreen composition` in visual prompts. Without this, Nano Banana defaults to 1:1 square. All production images must be 16:9. (Added 2026-03-07)
- **RULE:** Visual prompts must be CLEAN and TOOL-FRIENDLY. Image generators cannot process narrative metaphors, emotional states, character psychology, or dramaturgical commentary. Write only what is visually renderable: setting, character positions, objects, lighting, colors, composition. "Posture aggressive like a stubborn teenager who knows everything" = useless. "Leaning forward, one arm raised, chin up" = actionable. (Added 2026-03-10)
- **RULE:** When a reference image is provided to the image generator (e.g., Robotiko reference), do NOT repeat the character's full physical description in the prompt. Use a short identifier ("the chrome android") and let the reference image carry the visual details. Long descriptions compete with the reference image and confuse the model. (Added 2026-03-10)
- **RULE:** CHARACTER REFERENCE IMAGES FIRST. Before generating scene images, generate a standalone reference image for each episode-specific character group (e.g., sol-liberal group, wedding guests). Upload this reference image alongside the text prompt for every scene where that group appears. Without this, Nano Banana generates different-looking characters in every scene — breaking visual continuity. (Added 2026-03-13)
- **RULE:** ENVIRONMENT REFERENCE IMAGES FIRST. For locations that appear in multiple scenes (e.g., an industrial estate in S40-S44), generate a standalone environment reference image first. Upload this environment image alongside the text prompt for every scene set in that location. Without this, Nano Banana generates inconsistent environments across scenes sharing the same location. (Added 2026-03-13)
- **RULE:** START-END FRAME LOCATION CONTINUITY. When generating Start-End (Mode B) frame pairs or sequential transformation scenes, REFERENCE the first image in the prompt for the second image. This ensures: same mountain silhouette, same sky treatment, same ground texture, same scale figures, same composition framing. The transformation (object change) happens WITHIN a stable environment — the viewer's eye stays grounded. Proven technique: EP01 S71→S72 (61.png referenced in 63.png prompt) produced seamless 8→∞ transformation with identical Anatolian mountain backdrop. Also applies to multi-scene motifs: generate the "intact" version first, then reference it for "damaged/transformed" versions (EP01: 49.png intact stone 8 → 61.png cracked stone 8 → 63.png infinity — same location, 3-stage transformation). (Added 2026-04-07)

## CATEGORY: DURATION COVERAGE (Added 2026-02-27)

- **RULE:** 1 scene ≠ 1 clip. Always calculate scene duration (from timestamps) vs. tool capacity (5s or 10s). Scenes longer than 10s require multi-clip coverage with sub-clips.
- **RULE:** Mode C (Extension/Variable) does not exist as a real tool capability. All video generation tools produce fixed-duration clips: 5s or 10s. Plan accordingly.
- **RULE:** Speed ramp maximum is 1.5× slowdown (e.g., 10s clip → 15s). Beyond 1.5× looks unnatural.
- **RULE:** Multi-clip sub-clips must use varied camera moves — not identical repetitions of the same motion.
- **RULE:** When a sub-clip needs a new image, include a complete supplementary visual prompt inline in the motion script (with mandatory suffix). The motion script must be self-contained.
- **RULE:** Coverage target: total generated clip duration ≥ 95% of total music duration.
- **RULE (EP01 Technique):** SPEED VARIATION REUSE: Same image can be reused with different camera speeds to match musical tempo changes. Example: EP01 S33 (cable tunnel, slow dolly) → S36 (same tunnel, FAST dolly) syncs with "You race across each vast domain" as music accelerates. Camera speed change = emotional change. Same composition, different experience. Cost-effective and narratively powerful. (Added 2026-04-06)
- **RULE:** SACRED-ARCHITECTURE WORDS TRIGGER RELIGIOUS IMAGERY — "Cathedral" (and similar words: temple, shrine, basilica) pulls image generators toward stained glass, altars, and worshippers. For massive industrial interiors use "colossal iron vault" instead. Tested and confirmed during EP05 production (the iron vault location). (Added 2026-04-02 during EP05; recorded here 2026-07-05 — the rule lived only in session notes until a README review caught the gap.)
- **RULE:** Kling 3.0 Multi-Shot: Use for multi-clip shots where sub-clips share the same source image AND are all Kling 3.0. Produces one continuous video (max 15s), smoother transitions, lower credit cost. Segments can be 5-8s each. Mark as `Multi-Shot` (not `Multi-Clip`) in motion script. If sub-clips use different tools or different source images → standard Multi-Clip (separate generations). (Added 2026-03-08, tested on EP02 S34b+c)

## CATEGORY: MOTION PROMPTS (Added 2026-02-27)

- **RULE:** Motion prompts are fed directly to Kling/Veo. Write ONLY what the tool can see and execute. Pure visual + motion descriptions.
- **RULE:** NEVER include in motion prompts: musical instrument names (Hammond, fuzz guitar), character names (Robotiko, Mentor), narrative commentary, speed ramp technical notes, audience direction, poetic metaphors, timing cues (BPM, "on the downbeat").
- **RULE:** Musical context belongs in the "Musical Moment" field. Narrative context belongs in the "Scene Context" field. The Motion Prompt field is ONLY for the video generation tool.
- **RULE:** Describe characters by their visual appearance ("chrome android", "robed figure with glowing staff"), never by name.
- **RULE:** NEVER use split-screen / multi-panel compositions in motion prompts. Video generators cannot handle "zoom into left panel", "right panel slides off-frame", or any panel-based movement. If the source image is a split-screen, treat it as a single flat image and describe only simple camera movement + atmospheric motion (dust, smoke, light shifts). (Added 2026-03-07)
- **RULE:** Keep motion prompts SIMPLE. One primary action only. No complex choreography (character A does X while character B does Y while camera does Z). Video generators produce best results with: 1 camera move + 1-2 atmospheric elements (dust, smoke, light). If a scene requires complex action, simplify to the aftermath or a single key moment. (Added 2026-03-07)
- **RULE:** Motion prompts must be SHORT — max 2-3 sentences before the video suffix. Describe atmosphere + main action with strong keywords, NOT micro-level visual details. Video tools respond to mood words (glowing, hypnotic, charred, decay) better than literal descriptions (halftone dots large as coins, paper fibers visible as individual strands). Over-detailed prompts confuse the model. (Added 2026-03-09, EP02 S29 lesson)
- **RULE:** CHARACTER MOVEMENT DIRECTION must be EXPLICIT. "Steps through the doorway" is ambiguous — the video generator may move the character in the wrong direction. Instead, describe the full action sequence: "walks away from the table, exits the room through the doorway into daylight." Specify what the character moves AWAY FROM and TOWARD, not just the destination. Also specify where the camera stays: "the camera stays inside" prevents it from following the character out. (Added 2026-03-13, EP03 S03 lesson)
- **RULE:** HEAD TURN / GAZE DIRECTION must be EXPLICIT with screen coordinates and a named target. Vague phrases like "his eyes shift toward something," "looks away," "glances across the room," "notices her" produce random, unconvincing head movement — the tool has no anchor for direction or intensity. **FIX pattern (tested working on EP05 S22):** (1) Lock the body first: "remains in the exact pose pictured, [holding/standing/sitting] [specific posture detail]." (2) Use the phrase "slowly and deliberately turns his head toward" — the adverbs control speed and intentionality. (3) Specify screen direction explicitly: "toward the left side of the frame (screen-left)" or "toward the right side of the frame (screen-right)" — NEVER just "left/right" alone, because the tool confuses character's left/right with viewer's left/right. (4) Name the target already visible in the source image with a short identifying description: "looking directly toward the golden-brass female android standing in the distant background among the rows of desks" — this anchors the gaze to an existing element instead of letting the tool invent one. (5) Close the gaze with a lock phrase: "his glowing blue eyes lock onto her," "his gaze settles on the [target]." This 5-step pattern produces the clearest head-turn animations. (Added 2026-04-03, EP05 S22 lesson — "blue eyes shift away from the folders toward something across the office floor" was vague; screen-left + named target + lock phrase produced a perfect take)
- **RULE:** MUSIC-MOTION ENERGY SYNC — Motion Strength and camera choice MUST match the musical energy at that timestamp, not just the visual content of the frame. Check the `musical_metadata.json` energy field for each section. If the music is rising/peaking (energy: high, vocals rising, drums active), MS should be ≥4 and camera should NOT be Static unless there's a deliberate narrative reason (silence section, composite image). If MS ≤3 + Static camera + "no movement" prompt language all coincide during an energetic musical moment, the clip will look like a photograph with a Ken Burns zoom — breaking the music-visual contract. **CHECKLIST for every clip:** (1) Read the musical section's energy level. (2) If energy ≥ medium AND camera is Static → justify or change. (3) If MS ≤ 3 AND music is not quiet/silence → justify or raise. (4) Never write "no movement", "completely still", "neither figure moves" during energetic musical moments unless it's a deliberate contrast (like chorus + dead labor in S23). The musical metadata is our biggest pipeline innovation — it must drive motion decisions, not just duration coverage. (Added 2026-05-02, EP06 S11/S20/S33 lesson — multiple shots had low MS + Static during rising vocals, producing slideshow-like clips)
- **RULE:** ANTI-SPAWN GUARD — Every motion prompt MUST end with "Do not add extra characters. Keep everything as pictured." after the video suffix. Video generators (Kling, Veo, Seedance) spawn phantom characters in backgrounds — flickering, glitching figures that waste credits on retakes. This guard line prevents the tool from adding elements not present in the source image. Apply to ALL prompts, not just crowd scenes. (Added 2026-03-14, EP03 S22 lesson)
- **RULE:** CROWD SCENE MICRO-MOTION — In scenes with multiple characters, NEVER use plural group descriptions ("smiling touts", "beckoning men") or broad gestures ("leaning in", "gesturing warmly"). Instead: (1) specify exact character count and appearance ("four men in black vests"), (2) state "remain in their exact positions", (3) limit movement to micro-actions only (subtle head nods, slow head pan, slight tilt), (4) add environmental motion for liveliness (neon flicker, smoke drift) instead of character movement. Plural descriptions + broad gestures cause AI to spawn duplicate characters and distort limbs. (Added 2026-03-17, EP03 S22 lesson)
- **RULE:** FRAME-LOCKED CAMERA MOVES — When using Tilt Up/Down, Pan Left/Right, or any move that implies "revealing new content beyond the frame," video generators will FABRICATE content outside the source image boundaries (mountains, buildings, planets, UFOs, structures). This happens because the tool interprets the camera move semantically as "show new area." **FIX:** (1) Use the word "subtle" before the camera move to limit magnitude. (2) Add "strictly within the existing frame composition" to lock boundaries. (3) Include explicit prohibitions: "do not reveal new elements above/below/beside the frame, do not extend the [sky/ground/horizon], do not add [specific likely fabrications: mountains, structures, planets, objects]." (4) Reference existing elements explicitly: "the stars already visible," "the dust already in the frame." (5) Close with: "camera movement stays within the source frame." Apply this pattern to ALL tilt/pan moves on landscape or sky scenes where the tool might invent extensions. **ALTERNATIVE for tilt-up feel without fabrication:** Switch the camera move to Crane Up (tilt + zoom out) and start the prompt with a tight crop on the lower portion of the source, gradually widening to reveal the upper portion already present in the image. This creates the "looking up" feeling through reframing rather than boundary extension. (Added 2026-04-03, EP04 S37 lesson — Tilt Up on wasteland+sky was fabricating mountains and structures above the frame; Crane Up + tight-to-wide framing solved it)
- **RULE:** MODE B KEYFRAME LIMITS — Mode B (Start/End Keyframes) works reliably ONLY when the two keyframes share the same composition/environment and differ in ONE clear element (character state change, pose shift, single object transformation). Mode B FAILS when the two frames require BOTH environment shift AND complex action (e.g., close-up face in fog → wide workstation scene with cord cutting). Symptoms of failure: weird morphing mid-states, objects appearing pre-transformed, environments glitching into existence, confusing transitions that read as mistakes rather than intentional effects. **FIX:** Drop Mode B, switch to Mode A using whichever single frame carries the most narrative weight (usually the END frame). Express the intended transformation as a SINGLE PHYSICAL MOTION within that frame — e.g., instead of "face morphs into workstation and cord is cut," use just the workstation frame and describe "cord severs, cloud drifts upward like a released kite." The discarded keyframe image can remain as a dramaturgy/concept reference but is not used in the clip. Add a note in the motion script explaining the Mode B → Mode A downgrade so future sessions understand the decision. (Added 2026-04-03, EP05 S15 lesson — hacker mask close-up → workstation cord cutting was producing weird transitions; simplified to Mode A on 15b with cloud-release motion)
- **RULE:** COMPOSITE/SPLIT-WORLD IMAGES — "Describe what IS, not what HAPPENS" — When the source image already contains a narrative transition baked into the composition (two environments side-by-side, before/after split, dream-to-reality threshold, warm/cold color split), DO NOT write the transition as an action in the motion prompt. Words like "dissolves," "gives way to," "transforms into," "fades from X to Y," "transitions to" tell the tool to CHANGE the image — but the image is already complete, it needs no change. The tool will then try to "help" by modernizing, replacing, or morphing one side of the composition, breaking the intentional split. **FIX:** (1) Describe the current state as a locked fact: "two worlds already visible in the frame — [left description] on the left, [right description] on the right." (2) Lock the character and composition: "stands still in the exact pose pictured," "keeping the same composition intact." (3) Add explicit prohibition: "do not transform, morph, or replace either side. Both environments remain exactly as pictured." (4) Limit motion to atmospheric micro-elements within each zone (dust motes in the warm side, flicker in the cold side, subtle light breathing). The narrative transition lives in the dramaturgy and in CapCut editing — the motion prompt's job is only to animate the frozen moment. (Added 2026-04-03, EP05 S21 lesson — "iron vault dissolves into office" was causing tool to modernize the right side of a composite split-world image)
- **RULE:** [DISSONANCE] IS A LITERAL TOKEN — `tests/energy_motion_check.py` exempts a shot only when the exact string `[DISSONANCE]` appears in its Musical Moment line. Variants like `[DISSONANCE — intentional: …]` are invisible to the machine: the shot still warns, and the registry doctrine is silently skipped. Write the literal tag first, then the justification: `**[DISSONANCE]** — intentional: …`. Every tag earns a `_management/dissonance_registry.md` row the same day. (Added 2026-07-12, EP10 post-approval audit — S26/S27 were tagged in a bracket-variant format and never exempted; the registry had no EP10 rows despite the script claiming they were logged.)
- **RULE:** A FRAME CHAIN CONSUMES THE UPSTREAM LAST FRAME — chaining means the downstream clip's start frame IS the upstream clip's exported last frame. If every shot in a proposed chain has its own approved raw keeper and its own framing, the chain contradicts the asset table (the keepers would be discarded) and the SKILL's "when NOT to use: different camera angles" rule. Drop the chain; a shared environment reference carries the continuity. (Added 2026-07-12, EP10 audit — Chain 1 S15→S16→S17 listed per-shot start frames AND claimed chaining.)

## CATEGORY: PIPELINE & FILES

- **RULE:** Musical metadata JSON is all-in-one — produced by Claude via `_skills/robotiko-musical-metadata/SKILL.md` from human-provided BPM, Key, and timestamped lyrics. Never ask the human to add more data to it. It is complete as delivered.
- **RULE:** Never reference `video_strategy_rules.md` — it does not exist. All strategy rules are in `_management/pipeline_rules.md`.
- **RULE:** Seedance Multiframes costs ~565 credits per generation (~1130cr for 2 tests). CapCut Pro monthly budget is 1200cr. Never assign Multiframes for production — budget-destroying.
- **RULE:** Raw folders (`04_visuals/raw/`, `05_video/raw/`) are gitignored. Never try to commit files from these folders.
- **RULE:** Seedance 1.0 performs well on character/figure scenes (Robotiko, people) but POORLY on abstract/texture content (maps, macro surfaces, paper textures). For map/texture shots, prefer Kling 2.5 Turbo (static camera) or Kling 3.0 (camera movement). Reserve Seedance for character-focused scenes where its budget advantage matters. (Added 2026-03-09, EP02 S29 lesson)
- **RULE:** Selected files have no version suffix. `ep{XX}_s{XX}_selected.png` — not `ep{XX}_s{XX}_selected_v01.png`.
- **RULE:** Musical metadata JSON has no version suffix. It is always `ep{XX}_musical_metadata.json`.
- **RULE:** Never use generic "Kling AI Pro" in motion scripts. Always specify the exact model: **Kling 2.5 Turbo** for Static camera shots, **Kling 3.0** for shots with camera movement (zoom, dolly, tilt, crane, pan). Mode B (keyframe) shots always have camera movement → always Kling 3.0. (Added 2026-03-29, EP04 motion script correction)
- **RULE:** CLOSE THE METADATA GAPS IN MOTION SCRIPTS — Musical metadata JSON has 1s gaps between sections (by design — breaths/transitions). When generating a motion script, timestamps MUST be made contiguous (S01 ends at 0:14 → S02 starts at 0:14, not 0:15). Scene Duration = contiguous timestamp span. EP01-EP08 did this correctly; EP09-EP10 propagated the gaps, causing a 35s deficit in EP09's CapCut guide and complete vocal-sync loss. The `capcut_guide_validator.py` now catches this at CI. (Added 2026-07-25, EP09 edit sync bug)
- **RULE:** KLING CANNOT DO DELIBERATE HUMAN HAND GESTURES — asked for a small open-palm beckon ("come"), Kling produces presenter-style arm movement: broad, performative, TV-host energy. It animates *motion*, not *intent*. For a shot whose meaning lives in one specific hand gesture, go to Google (Veo / Gemini) instead, and accept the tool trade-offs (see the audio/resolution rule below). Content wins over pixels: a sharp clip with the wrong choreography is a failed shot; a soft clip with the right one is not. (Added 2026-08-04, EP10 S34b — the series' final beckon)
- **RULE:** GOOGLE-GENERATED CLIPS CARRY AN AUDIO TRACK — Veo/Gemini renders ship with synthetic ambience (AAC ~128kbps) while Kling clips are silent. In a music-video timeline that audio plays *under the score* if you do not detach or mute it on import. Check every non-Kling clip for an audio stream before assembly: `ffprobe -v error -select_streams a -show_entries stream=codec_name -of csv=p=0 <file>` (empty = silent). They also come in lower (720p) and much thinner (~2 Mbps vs ~11 Mbps) — grade and grain them against their direct neighbour, not against the episode reference. (Added 2026-08-04, EP10 S34b)
- **RULE:** MEASURE THE RENDERED CLIPS — never build a CapCut guide from the motion script's nominal `Clip Duration` column. The motion script *plans* 5s/10s tool outputs; production renders whatever the human actually generated (EP10: 3.04s / 6.04s / 8.04s / 11.04s clips, one at 720p instead of 1080p). Probe the real files before writing the Timeline Map — `ffprobe -v error -show_entries format=duration -of csv=p=0 <file>` for duration, `-select_streams v:0 -show_entries stream=width,height` for resolution. Consequences of skipping it: every Speed/Trim value is wrong, and a resolution outlier on a key shot ships unnoticed. EP10 planned 5 speed ramps; the measured clips needed 28. (Added 2026-08-04, EP10 CapCut guide)
- **RULE:** CLOSE THE GAPS BY EXTENDING, NEVER BY SHIFTING — when a motion script's gapped timestamps must be made contiguous at the edit stage, keep every scene's START time and run each scene to the NEXT scene's start. Scene starts are the beat-sync anchors and they land on musical section boundaries (EP10: all 9 boundaries were scene starts); shifting them to redistribute the deficit silently destroys every anchor in the Beat Sync table. The absorbed seconds become per-clip speed ramps, not moved cuts. (Added 2026-08-04, EP10 CapCut guide — 34s deficit absorbed across 28 fit ramps, all 15 anchors preserved)
- **RULE:** PIN THE BLOB, NOT THE WORKING COPY — approval-ledger sha256 pins must be computed from the LF-normalized bytes git stores (`git show HEAD:path | sha256`), NEVER from a Windows working copy: `.gitattributes` forces LF on sha-pinned text, so a CRLF working file hashes differently from what every fresh clone (and CI) receives. Symptom: local suite green, fresh-clone suite red on `test_ledger_sha_matches_disk`. Found 2026-07-12 — five pins (EP02-05 gate-1 + EP05 gate-2) had been re-baselined from CRLF disk copies; the repo-recreation fresh-clone verification caught it. Corollary: ALWAYS verify the suite in a fresh clone before go-public, not only in the working repo. (Added 2026-07-12)
- **RULE:** COMMIT-SHA POINTERS ARE REWRITE-MORTAL — every history rewrite re-hashes all descendant commits, so every in-repo doc pointer to a commit sha dies silently (found 2026-07-12: multiple dead pointers across tracked docs, orphaned by an earlier rewrite). After ANY rewrite: grep tracked *.md for sha-like tokens (excluding sha256 content pins and pinned action SHAs), resolve each by its commit-MESSAGE key, and update in one pass (the release runbook §7.10 — private). When writing a new pointer, always pair the sha with its commit message so the message key survives the sha.

## CATEGORY: WORKFLOW

- **RULE:** Three mandatory checkpoints exist. Never skip them:
  1. Dramaturgy must be human-approved before visual prompts begin.
  2. Reference Gate (1R, two-phase episodes, EP10 onward): reference images must be human-approved before Phase-2 scene prompts begin.
  3. Motion script must be human-approved before video generation begins.
- **RULE:** Always ask "Would Fibula approve this?" before delivering any output.
- **RULE:** If a task goes wrong mid-execution: STOP, re-plan, inform human, then continue.
- **RULE:** THINKING EFFORT — match the per-session reasoning effort (low / medium / high / extra high / max) to the task. **Single-shot deep synthesis → max** (dramaturgy, motion script: one irreversible pass reconciles music + arc + camera across the whole episode). **Iterative / conversational creative work → high** (concept notes, brainstorming, discussion — depth comes from back-and-forth, and high stays responsive). **Mechanical work → low/medium** (YouTube packaging, naming validation, file ops). Max never lowers quality — it only costs time/tokens — so spend it where one pass carries the most weight. Budget priority when constrained: Dramaturgy > Motion Script > Visual Prompts. (Added 2026-06-04 — full table in CLAUDE.md "Thinking Effort Protocol".)

## CATEGORY: IMAGE FIDELITY & REPRESENTATION (Added 2026-03-01)

- **RULE:** Video generators will attempt to "clarify" ambiguous visual elements (silhouettes → realistic people, blurred shapes → detailed objects). Motion prompts must explicitly protect abstract/intentional elements with preservation language: "maintain as featureless dark shapes, do not resolve into detailed figures."
- **RULE:** Source images are production-ready. Video generators must animate them faithfully — not reinterpret, enhance, or "improve" visual elements. If a background has abstract silhouettes, the video must keep them abstract.
- **RULE:** All crowd, audience, mob, and group scenes must include mixed gender representation. Never write "suited figures" or "strikers" without specifying "mixed men and women." This applies to both visual prompts and motion prompts.
- **RULE:** Background crowds in Davos scenes, protest scenes, mine scenes, and any public setting must reflect realistic demographics — not uniform rows of identical male figures.

## CATEGORY: CHARACTER DESIGN (Added 2026-03-23)

- **RULE:** Never write "amber eyes", "glowing [color] eyes", "aura around eyes", or "no glow/no luminescence" in visual prompts. Image generators render ANY eye glow description as literal glowing eyeballs = alien/creepy. Negative instructions ("no glow") cause the generator to latch onto the keyword "glow" and apply it. **WORKING FIX (tested 2026-03-31):** Describe eyes as a PHYSICAL MATERIAL: "dark amber glass lenses set into chrome sockets, like polished gemstones — warm brown-gold tone, reflective, catching the environment light on their smooth curved surface." The key: (1) "glass lenses" = solid material, not light source, (2) "dark amber" = warm but not luminous, (3) "like polished gemstones" = gives generator a non-glowing reference object, (4) "catching the environment light" = reflective, not emissive. Three failed approaches: "amber eyes" (v1), "warm glow radiating around eyes" (v2), "no glow, no luminescence" (v3 — produced cyan glowing eyes). (Added 2026-03-23, updated 2026-03-31 with confirmed working fix)
  - **UPDATE 2026-07-05 — this rule graduated from a documented Gap to MACHINE enforcement (ADR-0010).** A two-layer doctrine now governs eyes: CANON may describe the on-screen *appearance* (Robotiko's eyes do emit steady blue light — master.md keeps that language); but any MODEL-FACING string must use the material-lens idiom. Robotiko's blue formula parallels the proven Robochica one: "steady blue optical lenses set into chrome sockets, like polished sapphires" (flickering blue-red for the Phase-2 fracture; calm steady blue for Phase-3). The lint (`eye_glow_hits`) fires on a glow keyword within 3 tokens of an eye/lens word and runs on BOTH model-facing surfaces — `character_profiles.json` prompt fields (`scan_eye_glow`, FAIL — it is a live input) and Text Prompt blockquotes (`check_eye_glow`, FAIL for version-stamped files, WARN for shipped unstamped ones). Kintsugi body gold-glow is allowlisted; "light" (lens projection) is deliberately not a glow keyword. `character_profiles.json` and master.md were reconciled: appearance in canon, lenses in prompts.

## CATEGORY: VEO PROMPT FORMAT (Added 2026-04-03)

- **RULE:** Veo does NOT respond well to our standard motion prompt format (camera move + atmospheric description + video suffix). Gemini-optimized prompts work 100%. Use this dedicated Veo format for ALL Veo-assigned clips:
  ```
  Animated version of the attached image. Maintain 100% visual fidelity to the original scene. Do not add any new characters, people, or objects. The environment and background must remain completely static and unchanged.
  Action: [Specific motion description — explicitly state what stays still AND what moves, with direction and speed]. 35mm film aesthetic, heavy film grain, shallow depth of field, Kodachrome color palette.
  ```
- **KEY DIFFERENCES from Kling/Seedance prompts:** (1) Anti-spawn guard at TOP, not bottom. (2) "Animated version of the attached image" anchors to source. (3) "Action:" label separates motion instruction. (4) Explicitly state what does NOT move. (5) Shorter suffix without "Shot on" or "cinematic 16:9 framing". (Added 2026-04-03, human-tested with Gemini optimization — standard prompts produced garbage, this format produced perfect results)
- **RULE:** VEO DECAY SPAWN — Veo has a strong tendency to add "abandoned/aged/decrepit" atmospheric elements when the source image suggests an interior personal space or retro-analog environment. Most common unwanted additions: **water drops falling from ceiling, leaks, dripping moisture, wall stains, drifting cobwebs, peeling paint, dust cascades, rot**. This happens even when the source image is clean and the action description is minimal — Veo reads "retro/analog/old technology" cues and interprets them as "decayed." **FIX:** (1) Extend the top anti-spawn guard to specifically list forbidden decay elements: "Do not add water drops, leaks, dripping, moisture, or any decay elements that are not in the source image." (2) Avoid words that cue malfunction/arousal for decay: replace "flickers almost imperceptibly" with "glows steadily, warm and quiet" — any flicker/tremor description invites the tool to extend the malfunction to the environment. (3) Explicitly declare surfaces as intact at the end of the action block: "The ceiling, walls, and all surfaces remain completely static and dry." The word "dry" is especially important as a negative signal. Apply this extension to ALL Veo prompts for interior/personal/analog scenes, not just ones showing decay — prevention is cheaper than retakes. (Added 2026-04-03, EP05 S26 lesson — Veo added water drops from the ceiling in Robotiko's room despite minimal motion prompt; fix was tested and produced perfect results)

## CATEGORY: REFERENCE IMAGE WORKFLOW (Added 2026-05-01)

- **RULE:** PROMPT BREVITY WITH REFERENCE IMAGES — When uploading reference images alongside a text prompt, the text prompt must contain ONLY: (1) camera angle/shot type, (2) character position in frame, (3) character pose (1-2 words max). NOTHING ELSE before the suffix. No abstract directions ("the space between them is the composition"), no poetic descriptions ("diminished in the frame"), no narrative context ("first visible emotion"), no details the ref image already carries (damage descriptions, surface textures, lighting mood, environment layout). If it's visible in the reference image, don't write it. If it's a feeling or interpretation, don't write it. If removing the words doesn't change what the generator draws, cut the words. (Sharpened 2026-05-02 after EP06 S01-S10 test — even v02 prompts were still too verbose; user's actual working prompts were 40-50% shorter than v02.)
- **RULE:** PREVIOUS SCENE AS REFERENCE — Upload the previous scene's generated output as an additional reference image for the next scene. This creates a visual consistency chain: same office, same lighting, same desk layout carries forward through the ref image, not through text description. Discovered during EP06 S01-S10: user uploaded 8.png (S08 two-character shot) as ref for S09, producing perfect environment continuity without any environment description in the prompt. (Added 2026-05-02)
- **RULE:** CAMERA ANGLE FOR DESK SCENES — When the character reference image shows a front-facing pose but the scene requires the character seated at a desk facing a monitor, the generator will place the character facing the CAMERA instead of the monitor (because the ref image faces the camera). **FIX:** Explicitly specify rear/profile camera angles in the prompt: "three-quarter rear view", "profile shot from the side", "seen from behind", "over-the-shoulder". NEVER leave camera angle implicit for seated-at-desk scenes. Without explicit angle, the generator defaults to the reference image's front-facing orientation, producing absurd compositions where the character sits with their back to the desk.
- **RULE:** REFERENCE IMAGE UPLOAD GUIDE — Visual prompt files should include a per-scene guide specifying WHICH reference images to upload alongside each prompt (character ref only, env ref only, both, or none). This prevents the human from guessing which refs apply to each scene and reduces generator confusion from unnecessary reference uploads.
- **RULE:** DO NOT DESCRIBE WHAT THE REF IMAGE ALREADY SHOWS — If the character reference image has an antenna, do NOT write "antenna on the left side of his head" in the prompt — the generator interprets this as an instruction to ADD/EXAGGERATE the feature (e.g., turning a small built-in antenna into a long physical rod). The ref image carries the detail; describing it again causes literal over-interpretation. Same applies to: damage details, specific body parts, wires, scars. If it's in the ref, leave it out of the text. (Added 2026-05-31, EP07 S13-S14 — "antenna still extended" caused the tool to generate a comically long antenna)
- **RULE:** ANTI-RAIN GUARD — The word "wet" in street/city prompts triggers umbrella and active rain generation even when the intent is post-storm aftermath. **FIX:** Use "after rain" instead of "wet", and add explicit "no active rain falling, no umbrellas" guard. (Added 2026-05-31, EP07 S05 — 5-6 generations all produced umbrellas until the guard was added)
- **RULE:** PHASE-CORRECT CHARACTER REFERENCE FILE — `ref_robotiko_master.png` is the PRISTINE Phase 1 master (intact body, full antenna, both ears, clean wires). For ANY episode where Robotiko is @Damaged (Phase 2, EP07+), the correct reference to upload is `android_damaged.png` (+ alt angles `_2`, `_3`). Uploading the pristine master for @Damaged scenes produces a pristine Robotiko regardless of text descriptions — a continuity-breaking error. `ref_robotiko_master.png` is used ONLY when the scene intentionally shows a pristine Robotiko (e.g., EP08 S22 dream copies). For Phase 3 (Kintsugi, EP09 S27+), start from `android_damaged.png` and rely on text prompt + chain refs from the first gold scene onward — no Phase 3 reference file exists yet. **APPLIES TO:** Visual prompt files — every Image Reference Path and Upload field must reference the correct file. **FIX NEEDED IN EP09:** `ep09_visual_prompts_v01.md` was generated with `ref_robotiko_master.png` for all scenes — must be corrected to `android_damaged.png` for S01–S26 and adjusted for S27+ Phase 3 transition. Also add a CHARACTER REFERENCE — CRITICAL NOTE section (like EP08's) explaining the distinction. (Added 2026-06-21, EP09 visual prompts session — same error that EP08 caught and corrected, but the lesson was not recorded, causing recurrence.)
- **[SUPERSEDED 2026-06-28 — see updated single-figure rule below]** **RULE:** ANTI-SPAWN GUARD FOR IMAGE PROMPTS — Image generators spawn duplicate androids/robots in scenes. Add "only ONE chrome android, no second robot" explicitly to every single-character scene prompt. This is different from the motion prompt anti-spawn guard (which prevents background figure spawning in video) — this prevents the image generator from creating multiple copies of the main character. (Added 2026-05-31, EP07 S05/S11 — generator consistently spawned 2 androids without the guard)
- **RULE:** INTENTIONAL MULTI-FIGURE / GHOST-SELF EXCEPTION — The anti-spawn guard forbids UNINTENDED duplicate androids, NOT deliberate multi-figure compositions. When a scene intentionally shows the same character more than once (a self watching its own ghost/soul, a dream of copies), do NOT write "only ONE android" — instead specify the EXACT count and each instance's distinct treatment, and guard only against a THIRD/extra figure: e.g. "exactly TWO instances of the same android — one solid + damaged + seated, one translucent + see-through + ascending; no third figure, no other robots." Render a ghost/soul self as a SEE-THROUGH holographic spirit-double (sky/background visible straight through its glowing body, internal wires faintly showing) as a translucent composite/overlay LAYER — NOT a morph of the solid body (morphing two robots risks failure per MODE B KEYFRAME LIMITS). At the MOTION-SCRIPT stage the anti-spawn guard must KEEP the intended extra figure and forbid only a third — flag these shots so the guard is not applied blindly. (Added 2026-06-04, EP08 S30/S31 climax "the self watching its own liberation": a translucent ghost-Robotiko escapes the cage and flies free while the solid @Damaged body watches itself; revised from an earlier "soul-bird light-form, not a second robot" plan per director's direction, with a human-provided ghost-style reference image `ep08_ref_ghost_style.png`.)
- **RULE:** REAR-VIEW EAR DAMAGE FAILURE — When Robotiko is shown from behind with his head in frame, Nano Banana cannot render the missing right ear (the black band/cover over the shrapnel scar disappears — the head looks intact). **FIX:** For any behind-the-head shot, use camera angles that hide the defect: (1) **Low angle (camera below, looking up)** — the ear area falls above frame or is occluded by the head itself. Best for climbing/ascent scenes. (2) **Three-quarter rear left** — angle slightly to his LEFT side, showing the intact left ear; the damaged right side is on the far side. (3) **Below-head framing** — frame from shoulders down, body posture carries the meaning. NEVER use a direct rear shot with the full head in frame — the ear damage will vanish. Apply to ALL episodes, not just EP08. (Added 2026-06-04, rear-view reference image test — Nano Banana consistently fails to render the missing ear from behind)
- **RULE:** PROMPT FORMULA FOR IMAGE GENERATORS — Image generators (Nano Banana, Gemini) process literal object/texture tags, NOT literary prose. Prompts must follow this strict order: `[Camera/Shot Type] → [Main Subject + Physical Details] → [Action/State] → [Background/Setting] → [Lighting/Atmosphere] → [Guards] → [Style Suffix]`. **FORBIDDEN in prompts:** (1) Metaphors — "flowing river of pedestrians" produces literal water; use "dense crowd of pedestrians walking." (2) Contradictory terms — "chrome" + "rusted dark smudge" fight each other; use "oxidized metal" or "tarnished chrome." (3) Abstract size comparisons — "he is the smallest shape" confuses the tool; use "occupying less than 10% of the frame." (4) Poetic prose — "the fog simply wraps around the gesture, absorbing it — nothing parts, nothing answers" is noise; use "fog surrounding the raised fist, undisturbed." Keep prompts short, literal, comma-separated where possible. The AI reads tags, not poetry. (Added 2026-05-31, Gemini/Nano Banana feedback during EP07 S16 production — confirmed by tool developer)

- **RULE:** FRAME TO THE ENVIRONMENT REFERENCE — When a scene has an environment reference image, OPEN it and write the camera ANGLE / framing to match its geometry: where the camera sits, how the perspective lines run, where the depth goes. Character references are frontal portraits, so without an explicit angle the generator turns the character to face the camera and centers it — producing flat, symmetrical, identical frames every time. Specify the **angle** + subject **placement / orientation** (three-quarter / profile / frontal, off-center, eye-level / low / high) and the environment's leading lines. Do NOT specify camera MOVEMENT (pan / zoom / tilt / pull-back — that belongs to the motion script); leave breathing room for the move instead of naming it. Upload the matching env ref so the reference reinforces the angle. (Added 2026-06-28, EP09 S34 — the kintsugi workbench shot kept coming out dead-center and frontal across many tries until the prompt was rewritten as "three-quarter view from the front-left corner, the bench receding diagonally toward the shutter" to match `ref_workshop.png`; it locked on the first try. See visual-prompts SKILL Rule 4b.)
- **RULE:** ANTI-SPAWN GUARD IS REDUNDANT WHEN THE REF ESTABLISHES A SOLO FIGURE — The approved Nano Banana guard is `single figure composition, no additional characters` (NOT "only ONE android" / "no second robot", which backfire). But OMIT it entirely when a strong solo character reference + a clearly solo scene already establish one figure — the phrase is then just noise. Add it only when duplication is a real risk (no solo ref, or a scene/composition the tool tends to populate). (Clarified 2026-06-28, EP09 S34 — the phrase had been added reflexively to a shot whose kintsugi ref already established a single figure.)

- **RULE:** REFERENCE-FIRST, OR PAY THE RESHOOT TAX — Generate every NEW reference an episode needs (a new body state, a new location, a new group) BEFORE you author or generate scenes against it. EP09 was the most visually-novel episode (Phase 3 kintsugi body, new workshop interior + exterior, new onlookers group) and its prompts were written before those references existed — so every gold-body scene was conjured from long text on the WRONG (damaged) base, costing 8-10 regenerations each; nearly every scene needed a manual rescue, where EP01-08 hit ~65-70% image first-pass because their references were ready. A scene must frame to a reference that EXISTS (Rules 4b/4c), not conjure it from text. The validator now enforces this: `check_reference_first` fails when an episode has scenes in a phase whose dedicated reference is null or missing on disk. Corollary: it is HEALTHY (not failure) to discover at generation time that a prompt needs a better reference/frame and go back to update it — the flow is iterative. ([ADR 0007](../_management/adr/0007-reference-first-or-pay-the-reshoot-tax.md), 2026-06-29.)
- **RULE:** USE A PRIOR FRAME AS THE BASE IMAGE — to lock a composition OR chain a zoom-out. When an earlier generated frame already holds what you need — a fixed composition (threshold, camera position) or an established WORLD that must stay consistent as the camera moves — declare it as the BASE image ("Use 5.png as the base image") and describe ONLY the change. The base carries the ENTIRE frame (camera + interior + exterior), so do NOT re-describe what it already shows. TWO uses: **(1) LOCK a static frame** — reuse a prior composition, change only the light/state (EP09 S36: `5.png` as base locked the dawn-threshold on a one-line change; re-describing the exterior had made it drift). **(2) CHAIN a zoom-out / extra-wide pull** — use the previous (tighter) frame as base for the next (wider) one and just widen the framing, so the world stays identical as the camera pulls back (EP09 dawn pull: `5.png` → S36 → S37 → S38 with `37.png` as base — a seamless consistent pull-out). Stronger than an env ref for continuity (pins the full frame, not just the look) and keeps prompts short. (Added 2026-06-29, EP09 S36-S38.)
- **RULE:** REF-NOTE SYNC ≠ SCENE RECONCILIATION — Reference-first is now STRUCTURAL, not a hope. The visual-prompts skill is split into two phases: **Phase 1 authors and gates the references** (gate 1R — the human generates + approves the reference IMAGES, recorded as data in `approvals.json`), and **Phase 2 writes every scene against the REAL approved pixels** (v02). Editing a reference block's Environment-Geometry note is NOT the same as re-checking the scenes bound to that space — the REF B reframe (2026-07-07 / commit `9790a71`) updated the block while 40 scenes went un-re-verified. Why it used to slip: the old single-pass "Framing Pass" was explicitly "never a blocker," so it was skipped. **How to apply:** never treat a ref-note edit as done — re-verify EVERY scene in that reference's coverage-map row before delivery (the B-residue backstop). The coverage map (Phase 1) names exactly which scenes a late ref edit invalidates; Phase 2 IS the framing pass, so scenes are born framed to pixels that already exist. ([ADR 0013](../_management/adr/0013-two-phase-visual-prompts.md), 2026-07-07.)

- **RULE:** A GREEN THAT CHECKED NOTHING IS A FALSE GREEN — If a validator parses a
  file into zero units (zero scenes, zero prompts) it will report PASS over a
  totally unchecked file. EP06's ref-integrity was "green" for weeks only because
  its `#### S11` headers didn't match a parser that required `#### Scene S11`.

- **RULE:** CHECK THE METADATA, NOT JUST THE PROSE — The reference bug lived in the
  `Image Reference Path` / `Upload` fields; the text prompt said "chrome android"
  not "robotiko". A prose-only check is the wrong instrument for a reference rule.
  **FIX:** parse the structured fields and judge against a data source-of-truth
  (`phase_reference_map`). The short identifier names the subject; the uploaded
  reference carries the visual truth. (TAKE 02)
- **RULE:** DON'T KEY ON A SINGLE SYNONYM — Character checks keyed only on
  "robotiko" missed every prompt that says "the chrome android". Maintain the full
  identifier set `["robotiko", "chrome android"]`. (TAKE 01)
- **RULE:** GRADE THE GRADERS — A checker with no proof it works is a more confident
  way to be wrong. Every check needs a frozen BAD fixture it must fail and a GOOD
  fixture it must pass, plus an isolation test (fires when it should, silent when
  it shouldn't). Fixtures are immutable snapshots — never "fix" them. (TAKE 04)
- **RULE:** A RED TEST IS NOT ALWAYS A BUG — TRIAGE FIRST — Sweep every episode, then
  classify each red as FIX (real bug → correct it, text-only, keep shipped images),
  WHITELIST (intentional non-Robotiko subject → scene-pinned exception with a
  reason), or REFINE (the check over-fires → tighten it). Decide per-failure before
  changing anything. (TAKE 05)
- **RULE:** JUDGE THE CHARACTER, NOT THE SCENERY — A forbidden body-state word bound
  to scenery/effect ("pristine shelves", "translucent data", "iron walls becoming
  translucent") or negated ("not pristine") is not a character violation. The
  subject-guard neutralizes those; body words (chest, plate, chassis) stay policed.
  (TAKE 05, REFINE A)
- **RULE:** PHASE 1 IS NOT UNIFORM — EP01 is pristine, but canon says EP02–EP03
  already carry battle damage, so "cracked"/"rusted" are correct there, not
  violations. Forbidden body-state keywords are keyed PER EPISODE, not per phase;
  Phase-3 markers stay forbidden until the body reaches Phase 3. (TAKE 05, REFINE B)
- **RULE:** WHITELISTS ARE NARROW AND PINNED — Never "ignore pristine in this
  episode." Pin to specific scenes + keywords with a written reason
  (`phase_keyword_whitelist`), so a pristine-Robotiko slip anywhere else still
  fires. Never whitelist the reliable gate (ref-integrity) — only the heuristic
  text check. (TAKE 05)
- **RULE:** NO LOOSENING WITHOUT A BOTH-DIRECTIONS PROOF — Any change that makes a
  check pass more (a whitelist, a guard, a granularity tweak) ships with two tests:
  one proving it STILL catches a real bug, one proving it correctly IGNORES the
  intended case. (TAKE 06 guardrail)
- **RULE:** ONE COMMAND, ONE GATE, PINNED — All checks run through
  `python tests/run_all.py` (exit non-zero on any failure), wired into CI
  (`.github/workflows/validation_suite.yml`) to block on failure. Keep the code
  standard-library only (smallest attack surface); pin the Python patch version and
  pin GitHub Actions to immutable commit SHAs, not floating tags. (TAKE 06)
- **RULE:** GOVERNANCE IS HONEST ABOUT GAPS — A green CI run does NOT mean every
  Golden Rule is enforced. The Invariant Coverage Matrix marks each invariant as
  machine-checked / heuristic / human-gated / GAP. Anti-spawn phrasing, the eye-glow
  rule, and the motion video-suffix are currently GAPS — not enforced. Don't imply
  coverage you don't have. (TAKE 06)
  *(Update 2026-07-05: anti-spawn and the motion video-suffix graduated to Machine
  tier via `tests/motion_script_validator.py` in the 2026-07-04 audit-fix session; the
  eye-glow rule then closed too — now Machine via `check_eye_glow` / `scan_eye_glow`
  (ADR-0010), so all three original Gaps are shut. The rule's principle stands — the
  matrix, not the green run, is the coverage truth.)*
- **RULE:** WHEN YOUR OWN RULES CONTRADICT, SCOPE BY AUDIENCE — master.md REQUIRES the
  sanctioned Turkish attribution (names like Hacı Bektaş Veli, labels like "Turkish
  wisdom tradition"); production requires model-facing prompts to be plain-English
  ASCII. The contradiction dissolves once you scope by *who reads the string*: canon
  and direction notes (concept notes, dramaturgy, musical metadata, and the
  Dramaturgy Reference / Composition Notes lines INSIDE a visual-prompts file) keep
  the attribution; only the Text Prompt / Motion Prompt blockquotes must be ASCII.
  `prompt_hygiene_lint.py` reads ONLY those blockquotes and NEVER opens master.md or
  the direction notes — the canon is never punished. A scoped check is the resolution
  to a self-contradiction, not a compromise of it. ([ADR 0006](../_management/adr/0006-scoped-prompt-hygiene.md), TAKE 06)
- **RULE:** A SENTINEL-LESS v02 HAS TWO NEW FALSE-GREEN TRAPS — When authoring a Phase-2 `v02` (scenes present, Phase-1 sentinel removed), two parser gotchas silently un-check the whole scene set, and the suite still goes 10/10 green: **(1) Scene headers MUST be `#### S{NN}` (FOUR hashes).** `extract_scenes` keys on `####\s*(?:Scene\s+)?S\d{2}`; three-hash `### S01` headers parse to ZERO scenes -> the scenes-XOR-sentinel meta-test FAILs (the loud symptom) but in other paths this is a silent false green. **(2) NO TEMPLATE_MARKERS anywhere in the file** (`{XX}`, `auto-populated by Claude`, `Do not fill manually`, `[Claude generates`, `Shot X: ...`). Once the sentinel is gone, `is_unfilled_template` fires on ANY marker and the visual-prompt sweep prints `Skipping (unfilled scaffold template)` and validates NOTHING — a real false green (the run stays green while the suffix/eye-glow/ref-integrity checks never touch a single scene). Write concrete filenames (`ep10_s01_selected.png`), never `{XX}`. Corollary: never print the literal `**Text Prompt:**` marker in prose/checklists — the prompt-extractor matches it as a real (suffix-less) prompt and FAILs; write "the Text-Prompt marker" without the asterisks. Proof the file is actually being checked: `visual_prompt_validator.py --full` must print `File: .../ep{XX}_visual_prompts_v02.md` (not a Skipping line) and report the expected prompt count (EP10 = 46: 6 refs + 40 scenes). (Added 2026-07-07, EP10 Phase-2 authoring — hit both traps live; SKILL Phase-2 checklist updated.)

## CATEGORY: CONTENT-LAYER VALIDATION (Added 2026-07-04)

- **RULE:** LATEST VERSION ONLY — When a validator scans versioned files (e.g., `ep09_motion_script_v01.md` and `v02.md`), it must check ONLY the latest version per episode per kind. Older versions may contain intentional legacy issues (e.g., em-dashes in v01 as tutorial "before" evidence). Scanning all versions causes false failures on superseded files.
- **RULE:** ALTERNATIVE GUARD FORMULATIONS — Anti-spawn and other guard rules have a canonical form ("Do not add extra characters. Keep everything as pictured.") but episodes may use legitimate alternatives ("No third figure. Exactly two instances"). Validators must recognize both the standard guard and a curated list of alternatives rather than requiring the exact canonical string.
- **RULE:** SKILL VERSION DETECTION — Pre-SKILL-v2 episodes (EP01-EP02) were produced before video suffix and anti-spawn guard rules existed. Validators must detect SKILL version from file headers and apply WARN (non-blocking) severity for pre-v2 files, FAIL (blocking) for v2+ files. This prevents legacy files from blocking CI while still surfacing issues as warnings.
- **RULE:** SHIPPED FILE POLICY — Canon terminology corrections (e.g., station name standardization) ARE applied retroactively to shipped files to maintain a single source of truth. Cosmetic changes are NOT. The distinction: if a term contradicts master.md's canonical form, fix it everywhere; if it's just a style preference, leave shipped files alone.
- **RULE:** EVERY SKIP BRANCH NEEDS A FIXTURE — A skip message that never prints is a silent pass. The EP01 PDF-detection fix shipped in the 2026-07-04 audit session was inert for a day because `os.listdir` never saw the PDF inside `selected/` — the "explicit skip" existed only in intention, and no test asserted the message actually appears. Every skip/waiver branch in a validator must be locked by a meta-test that (a) triggers the branch on a fixture and (b) asserts the visible output text. Fixes are subject to the same verify discipline as features. (Added 2026-07-05, from the M4 inert-fix finding)
- **RULE:** LATE OVERRIDE = SAME-DAY UPSTREAM SWEEP — when the human overrides a locked guard at a late stage (raw review, motion script), the override must be swept into every upstream document that states the guard (dramaturgy, visual prompts, the motion script's own summary tables) as a dated exception note. A stale hard guard ("any smile = reject") left standing will cause a reviewer or a future session to reject the approved take. (Added 2026-07-12, EP10 audit — the S34b smile override lived only in the prompt + approvals note while three documents still said hard-reject.)

## CATEGORY: MUSICAL METADATA (Added 2026-07-06)

- **RULE:** BPM DETECTORS DOUBLE-COUNT HALF-TIME FEELS — Key/BPM tools (vocalremover.org etc.) read the subdivision, not the felt pulse: a slow power ballad or a heavy stomp-clap walking beat comes back at 2x its felt tempo. Symptom: the detected BPM contradicts the canon tempo language ("slow", "heavy & steady") or the mood. Treatment: keep the DETECTED value in `tempo` (it is the measurement, and downstream files may already use it), and record the felt pulse in a `styles` entry ("Half-Time Feel: detector reads NNN BPM double-time; felt pulse is NNN/2..."). Cut rhythm and beat-sync follow the FELT pulse. Confirmed cases: EP05 (122 detected / 61 felt, Anatolian blues groove), EP06 (134 detected / 67 felt, slow power ballad), EP10 (153 detected / 76.5 felt, stomp-clap walking song). Sanity check: tap-count the beat for 15 seconds and multiply by 4 before trusting the tool.

## CATEGORY: TERMINOLOGY & FRAMING (Added 2026-07-06)

- **RULE:** EP10 FORM TERMINOLOGY — Refer to EP10's poetic form ONLY as "answer-poem" or "answer-song" (with the Nimri Dede / "Turkish folk poetry" attribution per Golden Rule 9). The Turkish literary loan-word for this form is banned from every repo file and every commit message (Fibula, 2026-07-06). The commit-msg hook already strips it from messages; do not reintroduce it in file contents either. If it slips into an unpushed commit's file content, rewrite the local history before pushing.
- **RULE:** THEORY LABELS REQUIRE VERIFICATION — Before a scholarly label (Brechtian, Jungian, gestus, etc.) enters a repo file, verify it against the actual theory with an adversarial pass (one agent defends with citations, one attacks as a hostile examiner). Confirmed pattern from the 2026-07-06 Brecht audit: the DEVICE may qualify while the AFFECT inverts it (fourth-wall rupture = Brechtian device; warm invitation = un-Brechtian affect — own the inversion explicitly); the project's own cultural frame is often the stronger card (the tea-to-camera is Anatolian hospitality first, theory second); and the most famous name is not always the right one (the indifferent-worker figure is Bruegel's ploughman via Auden, not Brecht). Strongest verified anchor: Brecht's radio theory (1932, "organise its listeners as suppliers") + Benjamin's "Author as Producer" (1934) for the repo-goes-public finale.
- **RULE:** LYRIC-SHEET CONVENTIONS (decided 2026-07-06) — The lyric files follow the official-lyric-sheet convention, not strict phonetic transcription: print the standard WRITTEN form; sung elisions (a swallowed article, a compressed syllable) are not spelled out ("engraved in a billion cells" stays written with the article even though the vocal elides it — standard sung elision, same as any rap/rock lyric sheet). EXCEPTION: a prominent, characterful audible interjection IS transcribed ("Eh, shrapnel took away his ear", EP02 — comic-shrug register, with a transcript note). Shipped lyric sheets are edited ONLY to match the written work or the audible performance — never purely to fix grammar (the audio is the shipped artifact; grammar slips in sung English read as accent, and Glitch is Scripture applies to the voice too). Sha-pinned production documents (dramaturgy, motion scripts) keep their production-time quotes. — When canon attributes a line to a named poet/thinker, lead with the attested original-language line, then own the project's rendering explicitly ("in Robotiko's machine-tongue: ..."). Never italicize a project paraphrase as if it were the source quote.
